# 分析を始める前の設計

競輪の分析や予想で踏みやすい失敗は、どれも「調べ始める前に考えなかったこと」から来る: ラインのような基本の要因の見落とし、車番に入っている実力の配置の取り違え、級班をまたいだ得点の比較、構成の違い（初日は予選が多い、など）の見落とし、検出力の不足、並びが予想であることの見落とし。
クエリを書く前・集計を始める前に、下の設計メモを作ってオーナーに見せる。

このスキルのディレクトリから見て `../../` がリポジトリの根。事実はこのスキルに書かない。各項目で、示したファイルを読み、関係する知識を識別子つきで引く。

## 設計メモ（7項目）

1. **問い（ファンの言葉で）** — オーナーが知りたいことを、ファンの言葉のまま1〜2行で書く。言い方は `../../knowledge/domain/vocabulary.md` に従う。

2. **効きうる要因（レースの仕組みから）** — `../../knowledge/domain/mechanisms.md` と `../../knowledge/domain/rules.md` を読み、この問いの結果に効きうる要因を挙げる。少なくとも次を、この問いに当てはまるか1つずつ確かめる:
   - ライン: 位置（先頭・番手・3番手以降・単騎）、ラインの人数、競り。同じラインの選手の着順は連動する（`MECH-002`。大きさは `../../knowledge/domain/laws.md` か `../../candidates/lines.md`）
   - 主導権と展開: 先行・捲り・差し（`MECH-002`）
   - 車番の配置: ミッドナイトは得点順（`RULE-004`）、4・6・8番車の慣例（`RULE-005`）。車番の集計は実力の配置と区別できない（`MECH-003`）
   - 得点の尺度: 窓（当月＋前3ヶ月）、級班、昇降級の Δ（`RULE-002`、`RULE-003`）
   - 構成: 種目、車立て、時間帯、級班、グレード、開催の何日目か（`METH-003`）
   - ガールズかどうか（`RULE-009`）、バンクと天候
   - `../../candidates/` の、この問いに関係するテーマのファイルにある候補

   挙げた要因ごとに、比較でそろえるか、分けるか、無視してよい理由を書く。

3. **使う項目と、測りたいものとの差** — `../../knowledge/field-dictionary.md` で、使う項目が何を測り、何を区別できないかを引く。ファンの言葉と項目がずれていれば、そのずれを書く。
   並びを使うなら、本物の並び（lines 表）か、府県から推定した並びかを書く（`DATA-KD-003`）。`照合: 未照合` の項目で指標を作るなら明記し、映像での確認をオーナーに頼む。

4. **期間と取得元** — `../../knowledge/data/keirin-data.md` と `../../knowledge/sources/` を読み、実際にある日を確かめてから期間を決める（`DATA-KD-002`）。収集はまだ遡っている途中。本物の並びがある期間は短い。既存の調査の期間を書き写すときは、その理由を確かめる。

5. **研究の取り決め** — `../../knowledge/commitments.md` を読む。予想を扱うなら、各選手の1着・2着以内・3着以内の確率で出し、車券や回収率にしない（`COMMIT-001`）。結果を知識に残すかもしれないなら、`COMMIT-002` の基準と、公開してよいもの（`COMMIT-004`、`COMMIT-005`）を確かめる。

6. **測る前に決める基準と方法** — `../../knowledge/methodology.md` と `COMMIT-002` を読み、測る前に次を書く:
   - 確認済み・否定・保留の基準と、実質的な大きさ（`COMMIT-002`）
   - 実力をそろえる方法（得点や得点順位。`METH-002`）
   - 各レースの時点より前のデータだけで、選手の性質を判定し、予想を学習すること（`METH-005`）
   - 同じレースの選手を独立に扱わないこと（`METH-006`）
   - 個人差を問うなら、選手あたりの件数の分布、検出力、縮小推定、並べ替え検定（`METH-001`、`METH-004`、`METH-007`）
   - 同じデータで通説を次々に確かめるなら、前半と後半での再現（`METH-008`）

7. **この問いに効く、データから見えないもの** — `../../knowledge/blind-spots.md` から、この問いの結論を歪めうるものを挙げ、どちらの向きに歪めうるかを書く。

メモを見せて、オーナーの了承や指摘を受けてから、クエリや集計に進む。この環境にデータがないときも、同じメモを「進め方」として示す。

## 予想を組み立てるとき

設計メモに加えて、次を確かめる。

- 選手ごとの成績（勝率・連対率）だけで組み立てない。ラインの位置と連動を入れる（`MECH-001`、`MECH-002`、`METH-006`）。
- レースの中で確率が整合する形にする（全員の1着の確率の和が1。例: 順位ロジット）。
- 評価は対数損失・ブライアスコア・較正で、学習に使っていない期間で行う（`COMMIT-001`、`METH-005`）。

## 1つのレース・1人の選手を評価するとき

「このレースどう？」「この選手をどう見る？」のように、目の前の1レースや1人を評価する問いには設計メモを作らない。答えの中で、次の2つを数行で確かめるだけにする:

- 効きうる要因（設計メモの 2。とくにライン、車番の配置、得点の尺度）
- この評価に効くデータから見えないもの（設計メモの 7）

## 軽い問いのとき

数字を1つ確かめる、既知の事実を聞く、のような小さな問いには設計メモを作らない。知識を引いて簡潔に答え、必要なときだけ「効く要因・項目の意味・期間」の注意を1〜2行添える。
