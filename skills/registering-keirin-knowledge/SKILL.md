# 知識の登録と訂正

このスキルのディレクトリから見て `../../` がリポジトリ（keirin-research）の根。知識は `../../knowledge/` に、保留の候補は `../../candidates/` にだけ置く。
書くのは、いま正しいとされている事実で、経緯は git の履歴と keirin-platform の docs に任せる。コマンドはリポジトリの根で実行する。

## 新しく登録するとき

1. **書式を読む。** `../../knowledge/README.md` の書式・接頭辞と置き場所・必須キー・出典の書き方に従う。

2. **種類を決める。**
   - 公式の資料（規程、KEIRIN.JP の入門ページなど）かデータの構造で確かめた規則・事実は `RULE`（または `SRC-KJ`・`SRC-OP`・`DATA-KD`）。仕組みの説明は `MECH`。出典を付ける。
   - 統計的な傾向（「〜しやすい」）は、`COMMIT-002` の基準で判断がついたものだけを法則（`LAW`）にする。確認済みも否定も登録する。`検証の記録`（スクリプトの `keirin-platform:<パス>@<コミット>`、コマンド、期間、件数、95% 区間、前半と後半、測る前に決めた実質的な大きさ）と `判断が変わりうる条件` を書く。個人差なら `選手あたりの件数` と `検出力` も書く。
   - 判断がつかないもの、オーナーから聞いただけの通説は、知識にせず候補（`CAND`）として `../../candidates/` の該当するテーマのファイルに置く。
   - 映像や現地での観察は、keirin-data の観察記録（`OBS`）にする（`handling-keirin-observation-conflicts` の 5.）。

3. **公開してよい形にする。** このリポジトリは Public（`COMMIT-004`）。選手の名前、選手登録番号、レースと位置から選手を特定できる記述、収集データの抜き出し、ビューアの URL、内部 API の呼び出し方、オッズパークの文言を入れない。個人差は「あるかどうか」だけを書く（`COMMIT-005`）。

4. **識別子を取る。** `python3 tools/kb.py next-id <接頭辞>`（候補は `next-id CAND`）。

5. **下書きを見せる。** 必須キーをすべて埋めた下書きと、書き込むファイルを示す。関係する既存の知識があれば `依存` でつなぐ（候補には依存できない）。

6. **承認を得てから書き込む。** オーナーが承認するまで、ファイルを変えない。

7. **検査して PR を作る。** `python3 tools/kb.py check` と `python3 -m unittest discover -s tests` を通す。ブランチ（`docs/...`）を切り、署名つきでコミットする（メッセージは英語の Conventional Commits）。署名の設定は変えない。PR を作り、CI が通ったらマージする（`AGENTS.md` の開発ルール）。

## 法則を確かめ直すとき

`COMMIT-003` の時期（期替わりのあと、本物の並びが1年分そろったとき）に、`検証の記録` のスクリプトで、登録のあとに入ってきたデータを集計する。基準を満たさなくなったら候補に戻し、下の「訂正するとき」の手順で依存を洗い出す。

## 訂正するとき

1. **依存する知識を洗い出す。** `python3 tools/kb.py dependents <ID>` で、その知識に直接・間接に依存する知識を一覧にする。
2. **使う側の場所も確認の対象にする。** 訂正する知識と依存する知識の `出典` に書かれた、keirin-platform などの使う側の文書の場所を一覧に加える。そこに訂正前の記述が残っていないかを示す。
3. **訂正の下書きを見せ、承認を得てから反映する。** 訂正する知識、影響を受ける知識、使う側の場所をまとめて見せる。承認の後で書き換え、`kb.py check` を通して PR を作る。

## keirin-platform との分担

- 新しい発見の経緯（どう調べ、何が出たか）は keirin-platform の docs に、事実はこのリポジトリに登録する。
- 検証のスクリプトは keirin-platform に置き、出すのは集計値だけにする。
